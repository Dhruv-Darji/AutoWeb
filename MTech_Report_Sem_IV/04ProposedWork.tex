\chapter{Proposed Methodology}

\section{System Overview}

Figure \ref{fig:ProposeArchitecture} shows the end-to-end flow of the proposed system architecture. We keep the three-stage structure of Prune4Web \cite{zhang2025prune4web} (Planner $\to$ Filter $\to$ Grounder) as the base, and we add a \textit{DOM Delta} layer that works along with the DOM filter phase, and a \textit{Privacy Hub + HITL} layer that works along with the grounder. The goal of these two layers is to make Web-Automation more local, cheaper, and more privacy-aware.

  \label{fig:ProposeArchitecture}

The defined pipeline works for a single sub-task, where the planner decide what to do atthe current step using the user-given high-level task. The pipeline first planner gets input as the user-given high-level task, previous sub-tasks history, and the injected privacy directive. based on the generated plan, Policy confident, Policy risk values pipeline decides the next step (Privacy generation can be implemented at Grounder level as well, with sensitive data masking). HITL Gate uses the privacy-risk keyword list defined initially to decide whether to go for further processing in the pipeline. On the filter step, the DOM is extracted and compared against the previously stored snapshot to produce delta view, in which each element is tagged as added, modified, or unchanged. Structural UIDs (an MD5 hash over tag, id, name, xpath) are assigned to every element \cite{deng2023mind2webgeneralistagentweb}. The delta-aware filter then returns the top-20 elements using a hybrid keyword + MiniLM \cite{wang2020minilm}\cite{reimers2019sbert} scoring function. The local grounder (a QLoRA-fine-tuned Qwen3-0.6B or Qwen2.5-0.5B) map the final element and generate action value to be performed.


\section{DOM Delta Processing}


At the sub-task level, we store the previous DOM value in memory as a snapshot to just compute the DOM difference and not to re-process the entire DOM on every step.
DOM Delta processing uses a cheap in-memory snapshot of the previous step's DOM and compares that with the current step's snapshot, and computes DIFF, so the filter can focus only on what has changed rather than repeatedly re-rank elements which were already ranked in the previous step.

We implemented the following three changes. First, for every interactive element we assigned a \textit{structural UID} computed as an MD5 hash of its tag, element id, name, and XPath. This UID depends on the structure of the DOM and not on content inside it, as a result, the same button keeps the same UID across re-renders even if its visible text mutates. This is the same stability property that Mind2Web's \texttt{backend\_node\_id} provides through the Chrome DevTools Protocol \cite{deng2023mind2webgeneralistagentweb}, but computed directly from parsed HTML so it works without a live browser on given datasets. Second, each element carries a compact \textit{ancestor summary} (up to four semantically meaningful ancestors such as \texttt{form}, \texttt{nav}, \texttt{section}, \texttt{dialog}) which is appended as a short suffix like \texttt{ctx=form\#signup > fieldset[Address]}. This contain the hierarchical meaning of the DOM. Third, Generate score of each candidate using a hybrid function,
\[
\mathrm{score}(e) = \alpha \cdot \mathrm{norm}(\mathrm{kw}(e)) + (1-\alpha) \cdot \mathrm{cos}\big(\mathrm{emb}(\mathrm{task}),\mathrm{emb}(e)\big),
\]
with $\alpha = 0.6$. Here the Sentense embeddings (emb) generated with \texttt{all-MiniLM-L6-v2} encoder \cite{wang2020minilm}, which is capabable to check semantic similarity with less latency than BERT models with comparable accuracy. Hybrid combines two strategies. where the keyword (kw)  preserves exact-match strength, while the embedding term captures paraphrases, such as task "sign in" against element text "Log in" or task "purchase" against element text "Checkout", that keyword matching misses. hence embedding matching can better map the planner plan with the DOM with meaning depth as well, which comes with higher embedding generation time.

Figure \ref{fig:DomDelta} sketches the three-way fusion of structural UID tracking, keyword scoring, and MiniLM semantic scoring. The combination keeps candidate-set construction deterministic and keeps the expensive semantic step (MiniLM inference on candidate summaries) inside a single batched forward pass, which measurements in Chapter 5 place at roughly 220~ms per step on an RTX 4050 - well inside the normal per-step budget of a web agent loop.

\section{Human-in-the-Loop with Privacy Hub}

Privacy Hub is a centralized privacy rools and lists risky of risky keywords such as CAPTCHA, Login, etc. Prune4Web and related systems. Privacy HUB also allows user customization, can be contain a complete site policy as well (which increases token usage). The layer is completely flexible and can be implement at the planner or grounder level, as per the requirement. Planner-level implementation will stop further steps as it triggers after just the planner result, and hence reduces inference time. While grounder-level implementation contain element masking (email addresses, phone numbers, date of birth, ID numbers, password placeholders) before prompting values straight into the LLM prompt. which can be use as  PII. A PolicyHub introduces a risk-based HITL gate and a Privacy-Aware LLM wrapper that rewrites the prompt before the call.

\textbf{PolicyHub and the risk-based HITL gate.}
The PolicyHub contain a set of defined policy rules and a lists of risky keyword  (payments, credentials, CAPTCHA, destructive actions, and account changes). The LLM's JSON output is extended with extra fields, \texttt{policy\_risk} (a self-reported boolean to tell to trigger risk), \texttt{risk\_confidence} (How much riskness LLM can infer confidently)  and \texttt{hitl\_reason} (a short string about why HITL trigger). The gate check for three independent triggers, OR-combined: (a) the LLM will decide and self-flag the sub-task as policy-risky, (b) one of the defined risk keywords appears in the action text or in \texttt{hitl\_reason}, or (c) the LLM's self-reported confidence is below a defined threshold value. If any trigger fires, the sub-task is further handed over for user interaction and user further independently performs on the browser. The gate deliberately sits \textit{before} the grounder rather than after it, so that risky actions are caught without spending the more expensive grounder call. We can customize layer to use in between both, even where \texttt{Privacy-Aware LLM wrapper} Sitting between the Filter and the Grounder. the Privacy-Aware LLM wrapper runs a PrivacyPipeline over every candidate element summary and over the assembled prompt. The pipeline has A PII detector applies a set of regex patterns for email, phone (US), SSN, credit card, IPv4, date of birth, passport, Aadhaar, PAN, and explicit password fields, and replaces any matches with placeholder tokens such as \texttt{[EMAIL\_MASKED]} or \texttt{[PHONE\_US\_MASKED]} and adding a short privacy directive into LLM prompt by which LLM does not generate masked token value and instead it treat masked token as it is.

% A $(\epsilon, 0)$-differential-privacy layer is available for the candidate ranking score vector, adding Laplace noise with scale $\mathrm{sensitivity}/\epsilon$ so that per-element scores carry formal privacy guarantees when that is appropriate for the deployment context \cite{dettmers2023qlora}. A short privacy directive is injected into the grounder's system prompt, instructing the model to treat placeholder tokens as opaque identifiers and not to attempt reconstruction.

\section{Implementation Notes}

The backbone of the pipeline is re-implemented from the Prune4Web paper \cite{zhang2025prune4web}, with deviations. In implementation at the Grounder stage supports a QLoRA-fine-tuned Qwen2.5-0.5B or Qwen3-0.6B adapter loaded in 4-bit nf4 quantisation via \cite{dettmers2023qlora}, running under 1~GB VRAM on an RTX 4050 (6 GB). The local grounder LLM  is fine-tuned on 6,626 Mind2Web-Multimodel examples using the identical Grounder prompt used at inference, so there is no train/inference drift. We reported the measured accuracy, training time, and latency trade-offs between the two local base models and the paper's fine-tuned Qwen2.5VL-3B-Instruct grounder \cite{zhang2025prune4web} in the next Chapter.
