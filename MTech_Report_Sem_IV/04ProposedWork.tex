\chapter{Proposed Methodology}

\section{System Overview}

Figure \ref{fig:ProposeArchitecture} shows the end-to-end flow of the proposed system. We keep the three-stage structure of Prune4Web \cite{zhang2025prune4web} (Planner $\to$ Filter $\to$ Grounder) as the backbone, and we add two new layers on top: a \textit{DOM Delta} layer that sits on the filter side, and a \textit{Privacy Hub + HITL} layer that wraps the grounder call and the final action execution. The goal of these two additions is to make the pipeline cheaper to run on large pages (by cutting down what the grounder has to look at across steps) and safer to run on real user sessions (by masking PII before it reaches the LLM and by gating risky actions before they are executed).

A single step of the proposed pipeline works as follows. The user's natural-language task plus the previous action history is passed to the Planner, which emits one imperative sub-task. The current DOM is extracted and compared against the previous snapshot to produce a delta view, in which each element is tagged as added, modified, or unchanged. Structural UIDs (an MD5 hash over tag, id, name, xpath) are assigned to every element, which gives us a stable identity across re-renders \cite{deng2023mind2webgeneralistagentweb}. The delta-aware filter then returns the top-20 candidates using a hybrid keyword + MiniLM \cite{wang2020minilm} \cite{reimers2019sbert} scoring function. Before those candidates go to the grounder, the Privacy Hub masks any PII found in element attributes and injects a short privacy directive into the system prompt. The local grounder (a QLoRA-fine-tuned Qwen2.5-0.5B or Qwen3-0.6B) emits a JSON action object along with a self-reported confidence and a boolean \texttt{policy\_risk} flag. The HITL gate consumes that output together with a policy-risk keyword list and decides whether to execute the action, block it, or escalate it to a human reviewer. Only when the gate clears does the action reach the browser driver.

\section{Novelty 1: DOM Delta Processing}

The first new layer addresses the stateless-DOM gap identified in Chapter 3. In most multi-step web tasks, the page changes only in a small region between one step and the next; yet all recent DOM-reduction approaches \cite{zhang2025prune4web} \cite{lai2024autowebglm} \cite{schiepanski2025d2snap} re-process the entire DOM on every step. DOM Delta Processing keeps a cheap in-memory snapshot of the previous step's DOM and compares it to the current snapshot, so the filter stage can concentrate on what actually changed rather than repeatedly re-ranking elements that were already ranked in the previous step.

Three small design decisions make this practical. First, every interactive element is assigned a \textit{structural UID} computed as an MD5 hash of its tag, element id, name, and xpath. The UID depends on structure and not on content, which means that the same button keeps the same UID across re-renders even if its visible text mutates. This is the same stability property that Mind2Web's \texttt{backend\_node\_id} provides through the Chrome DevTools Protocol \cite{deng2023mind2webgeneralistagentweb}, but computed directly from parsed HTML so it works without a live browser. Second, each element carries a compact \textit{ancestor summary} (up to four semantically meaningful ancestors such as \texttt{form}, \texttt{nav}, \texttt{section}, \texttt{dialog}) appended as a short suffix like \texttt{ctx=form\#signup > fieldset[Address]}. This borrows the hierarchical-disambiguation idea of HTML-T5 \cite{gur2024webagent} but achieves it through prompt-level text rather than model fine-tuning. Third, the filter scores each candidate using a hybrid function,
\[
\mathrm{score}(e) = \alpha \cdot \mathrm{norm}(\mathrm{kw}(e)) + (1-\alpha) \cdot \mathrm{cos}\big(\mathrm{emb}(\mathrm{task}),\mathrm{emb}(e)\big),
\]
with $\alpha = 0.6$ and sentence embeddings produced by the compressed \texttt{all-MiniLM-L6-v2} encoder \cite{wang2020minilm}. The keyword term preserves exact-match strength (which is what Prune4Web relies on), while the embedding term captures paraphrases, such as task "sign in" against element text "Log in" or task "purchase" against element text "Checkout", that keyword matching misses.

Figure \ref{fig:DomDelta} sketches the three-way fusion of structural UID tracking, keyword scoring, and MiniLM semantic scoring; the source file is provided separately as \texttt{diagrams/fig\_4\_2\_dom\_delta.mmd}. The combination keeps candidate-set construction deterministic and keeps the expensive semantic step (MiniLM inference on candidate summaries) inside a single batched forward pass, which measurements in Chapter 5 place at roughly 220~ms per step on an RTX 4050 - well inside the normal per-step budget of a web agent loop.

The expected payoff is smaller input to the grounder, which is the stage where LLM tokens actually get spent, while keeping recall on the ground-truth element. Chapter 5 reports a 16 to 18\% token reduction at matched or slightly improved Recall@20 across all three Mind2Web test splits and a +1.20~pp improvement on the largest (test\_domain, 3{,}838 samples).


\section{Novelty 2: Human-in-the-Loop with Privacy Hub}

The second new layer addresses the privacy/safety gap. Prune4Web and related systems \cite{zhang2025prune4web} \cite{lai2024autowebglm} send element summaries that often contain PII (email addresses, phone numbers, date of birth, ID numbers, password placeholders) straight into the LLM prompt, and have no mechanism to distinguish a harmless "click the menu" action from a "submit payment" action. The proposed system introduces two cooperating components to fix both of these at once: a PolicyHub that drives a risk-based HITL gate, and a Privacy-Aware LLM wrapper that rewrites the prompt before the call.

\textbf{PolicyHub and the risk-based HITL gate.}
The PolicyHub carries a set of default policy rules and a 24-keyword risk dictionary covering payments, credentials, CAPTCHA, destructive actions, and account changes. The Planner's JSON output is extended with two extra fields, \texttt{policy\_risk} (a self-reported boolean) and \texttt{hitl\_reason} (a short string), in addition to the standard \texttt{sub\_task}, \texttt{action\_type}, \texttt{value}, \texttt{reasoning}, and \texttt{confidence}. The gate evaluates three independent triggers, OR-combined: (a) the LLM self-flagged the action as policy-risky, (b) one of the 24 risk keywords appears in the action text or in \texttt{hitl\_reason}, or (c) the LLM's self-reported confidence is below a configurable floor (default 30). If any trigger fires, the action is routed to human review; otherwise it proceeds to the grounder. The gate deliberately sits \textit{before} the grounder rather than after it, so that risky actions are caught without spending the more expensive grounder call. An earlier composite-confidence formula was discarded during design because it conflated uncertainty (a low-confidence but safe action is fine to execute) with risk (a high-confidence but dangerous action still needs review); splitting these into three independent rules captures the intent more cleanly.

\textbf{Privacy-Aware LLM wrapper.}
Sitting between the Filter and the Grounder, the Privacy-Aware LLM wrapper runs a PrivacyPipeline over every candidate element summary and over the assembled prompt. The pipeline has two parts. A PII detector applies a set of regex patterns for email, phone (US), SSN, credit card, IPv4, date of birth, passport, Aadhaar, PAN, and explicit password fields, and replaces any matches with placeholder tokens such as \texttt{[EMAIL\_MASKED]} or \texttt{[PHONE\_US\_MASKED]}. A $(\epsilon, 0)$-differential-privacy layer is available for the candidate ranking score vector, adding Laplace noise with scale $\mathrm{sensitivity}/\epsilon$ so that per-element scores carry formal privacy guarantees when that is appropriate for the deployment context \cite{dettmers2023qlora}. A short privacy directive is injected into the grounder's system prompt, instructing the model to treat placeholder tokens as opaque identifiers and not to attempt reconstruction.

\section{Implementation Notes}

The backbone of the pipeline is re-implemented from the Prune4Web paper \cite{zhang2025prune4web}, with two deliberate deviations. First, the filter LLM emits a \texttt{\{keyword: weight\}} dictionary which a fixed deterministic Python scorer then executes, rather than the LLM emitting a complete Python function that is evaluated at runtime. The economic argument of Prune4Web (the LLM never sees the raw DOM) is preserved, while the attack surface of arbitrary code execution is removed. Second, the Grounder stage supports a local backend: a QLoRA-fine-tuned Qwen2.5-0.5B or Qwen3-0.6B adapter loaded in 4-bit nf4 quantisation via \cite{dettmers2023qlora}, running under 1~GB VRAM on an RTX 4050 (6 GB). The local grounder is trained on 6{,}626 Mind2Web examples using the identical \texttt{GROUNDER\_SYSTEM} prompt used at inference, so there is no train/inference drift. Chapter 5 reports the measured accuracy, training time, and latency trade-offs between the two local base models and the paper's fine-tuned Qwen2.5VL-3B-Instruct grounder \cite{zhang2025prune4web}.
