\chapter{Literature Survey}

\section{Early Automation} 

Early-stage automation relied on random, rule-based, and script-based strategies. These methods had notable limitations and do not provide high flexibility and scalability.

\begin{enumerate}
    \item \textbf{Random-based automation} Random testing is helpful for identifying bugs that structured automation may miss \cite{RandomTesting:inproceedings}. Applying a random operation on the GUI is the idea for the random-based automation. It is not the best tool due to its highly redundant and useless action performance.
    \item \textbf{Ruled-based automation} Ruled-based automation is planned automation with idea to apply rules on known UI structure \cite{RuledBasedAutomation}. It is a widely used testing strategy for exploring testing and bug detection
    \item \textbf{Script-based automation} To control GUI interactions, script-based automation uses code scripts.  Java binaries and the JVM are used by programs like jRapture \cite{ScriptBasedAutomation} to record and replay Java-based GUI sequences, allowing consistent execution by accurately replicating input sequences.
\end{enumerate}



\section{Shift Toward Intelligent GUI Automation} 
Machine Learning and Deep Learning based approaches motivate intelligent GUI automation. Furthermore, LLM and MLLM enhance this field with large prompt and visual input capabilities.\\ 
\textbf{GPT‑4V(ision) is a Generalist Web Agent, if Grounded (SeeAct):}\\
SeeAct \cite{SeeAct} is foundational work showing that the large multimodal models like GPT-4V can act as generalist web agents. It uses both visual and textual values to generate actions and use the Plawright environment for action executions \cite{SeeAct}. The paper achieve 51.1\% accuracy on online evaluation, which is 20-30\% improvement over only text-based methods \cite{SeeAct}. The paper also shows that grounding remains the main bottleneck and possible improvement suggestion on grounding \cite{SeeAct}. \\
\textbf{AdaptAgent: Adapting Multimodal Web Agents with Few‑Shot Learning from Human Demonstrations:}\\
This paper addresses a key limitation of SeeAct for unseen websites or domains. AdaptAgent proposes a few-shot learning based method over a new website or domain \cite{FewShotLearning:verma2024adaptagentadaptingmultimodalweb}. Experiments on standard benchmarks show that even with few shots, agents improve success rate by 3.36\% to 7.21\% \cite{FewShotLearning:verma2024adaptagentadaptingmultimodalweb}.
This suggests that few-shot adaptation is a promising, efficient way to make MLLM-based agents more robust across diverse websites, instead of relying solely on large-scale fine-tuning.\\
\textbf{Browsing Like Human: A Multimodal Web Agent with Experiential Fast-and-Slow Thinking (WebExperT):}\\
The goal of this latest effort is to improve web agents' human-like reasoning.  The authors present a dual-process planning paradigm: "fast" initial passes and "slow" deliberation when necessary \cite{Browsinglikehuman:luo2025browsing}. It also incorporates experience learning, whereby the agent considers its past mistakes and modifies its behaviour going forward \cite{Browsinglikehuman:luo2025browsing}.  WebExperT outperforms baseline multimodal agents on the Mind2Web benchmark \cite{Browsinglikehuman:luo2025browsing}. WebExperT greatly increases the sophistication of multimodal online agents by combining memory, reflection, and a human-like reasoning style.


\section{Structural DOM Pruning and Local Grounding}
Real-world web pages often contain 10,000 to 1,00,000 DOM tokens \cite{zhang2025prune4web}, which is much larger than the practical input size of LLMs, and because of this, a recent line of work has focused on reducing the DOM representation before it reaches the model. \\
\textbf{Prune4Web:}
Prune4Web \cite{zhang2025prune4web} proposes a meta-programming style filter, where the LLM emits a small keyword/weight scoring script and a deterministic Python scorer executes it over the DOM. This keeps the raw DOM out of the LLM context entirely at the filter stage and still achieves 25x to 50x candidate reduction with a reported Element Accuracy of 88.28\% on Mind2Web using a Qwen2.5VL-3B-Instruct vision-language grounder that the authors fine-tune themselves; they also show that a lighter Qwen2.5-0.5B-Instruct variant works in the same pipeline \cite{zhang2025prune4web}. It is the closest work to our proposed system and the direct starting point for our implementation.\\
\textbf{AutoWebGLM:}
AutoWebGLM \cite{lai2024autowebglm} takes a different route and uses an HTML pruning algorithm that iteratively trims non-actionable nodes, limits tree depth, and keeps only nodes with actionable descendants. The observation given to the model is task description, simplified HTML, viewport info, and previous action history. DOM processing is still stateless in the sense that every step simplifies the full current DOM from scratch \cite{lai2024autowebglm}.\\
\textbf{Agent-E:}
Agent-E \cite{tarsariya2024agente} condenses the DOM using the accessibility tree and role-based filtering, which exposes only the actionable subset of elements to the LLM. It is also the only published system that explicitly monitors DOM changes between steps, using the browser's MutationObserver API \cite{tarsariya2024agente}. However, the observed change is converted into a natural language description and appended to the next prompt, which increases tokens rather than reducing them \cite{tarsariya2024agente}. Agent-E reports 73.2\% success rate on WebVoyager \cite{tarsariya2024agente}.\\
\textbf{HTML-T5 / WebAgent:}
WebAgent \cite{gur2024webagent} argues that flat element lists lose information that the DOM tree carries, and fine-tunes an HTML-specific T5 variant on long HTML token sequences to encode ancestor chains for each element. This is effective for disambiguation between visually identical elements (for example, an "email" input inside a login form versus a newsletter form), but it is model-specific and requires expensive training on full HTML \cite{gur2024webagent}.\\
All of these systems share a common property: each DOM snapshot is processed in isolation, without using the temporal relationship between consecutive page states.


\section{DOM State-Change Representations}
A smaller body of work looks at how to represent what changed between two snapshots of the same page, which is relevant both for agent reasoning and for token cost. \\
\textbf{D2Snap:}
D2Snap \cite{schiepanski2025d2snap} is the first algorithm specifically designed for DOM downsampling of LLM-based web agents. It walks the tree in post-order and applies three operations: merging containers hierarchically, dropping low-relevance text using TextRank, and filtering attributes below a semantic threshold derived from GPT-4o \cite{schiepanski2025d2snap}. An adaptive wrapper, AdaptiveD2Snap, tunes the three parameters to hit a target token budget, pushing the DOM size to roughly $10^3$ tokens, which matches the token order of grounded GUI screenshots \cite{schiepanski2025d2snap}. The method, however, operates on static snapshots in isolation; it contains no mechanism for tracking state change across consecutive agent steps \cite{schiepanski2025d2snap}.\\
\textbf{Agentic Compilation:}
Agentic Compilation of Web Interfaces \cite{agenticcompilation2025} discusses DOM diffing, prompt compression, and partial state caching as production-oriented mitigations in its related work, but it does not implement DOM diffing; its own contribution is a DOM Sanitisation Module that achieves up to 85\% token reduction through per-step noise removal and attribute cleansing \cite{agenticcompilation2025}.\\
\textbf{Classical Tree-Edit-Distance:}
On the algorithmic side, Tree Edit Distance (TED) \cite{zhangshasha1989ted} is the canonical algorithm for comparing two tree structures and recovering the minimum-cost sequence of insert/delete/rename operations; RTED \cite{pawlik2011rted} is the current state-of-the-art variant with better worst-case performance on skewed trees. These algorithms inform the kind of structural differences one could classify between two DOM snapshots, but they were not designed with the real-time token budget of a web agent in mind.\\
None of the DOM-diff approaches above are wired into the filter stage of an LLM web agent, which leaves an open design space for using cross-step structural change as a candidate-reduction signal rather than as an action-feedback signal.


\section{Semantic Relevance and Local Grounding Models}
Current element-relevance scoring in web agents relies mostly on keyword matching (Prune4Web) or fine-tuned cross-encoders (Mind2Web), and none of them apply general-purpose sentence embeddings to the DOM. \\
\textbf{Sentence-BERT:}
Sentence-BERT \cite{reimers2019sbert} establishes the siamese/triplet encoding technique that turns sentences into dense vectors usable with cosine similarity, and shows that late fusion of sparse (keyword/BM25) and dense (embedding) scores usually beats either one alone on retrieval tasks \cite{reimers2019sbert}.\\
\textbf{MiniLM:}
MiniLM \cite{wang2020minilm} distils large Transformer encoders into small task-agnostic ones. The widely used \texttt{all-MiniLM-L6-v2} checkpoint has 6 layers and $\sim$22M parameters, fits under 100~MB, runs at roughly 2~ms per sentence on CPU, and ranks near the top of sentence similarity benchmarks for its size class \cite{wang2020minilm}. These properties matter because a web agent loop has a few-second per-step budget, and a heavier encoder would eat that budget on element ranking alone.\\
\textbf{QLoRA and small open grounders:}
On the grounder side, QLoRA \cite{dettmers2023qlora} showed that 4-bit quantisation of the base model combined with LoRA adapters makes it practical to fine-tune billion-scale models on a single consumer GPU with only a small accuracy gap to full-precision tuning. This is what allows us to train a sub-1B grounder locally instead of depending on a paid hosted model. The Qwen2.5 \cite{qwen25techreport2024} family (and the more recent Qwen3 family) provides permissive, instruction-tuned open-weight bases in the 0.5B to 0.6B range that are realistic targets for such local fine-tuning.

\section{Critical Research Gaps \& Motivation for Our Work}
Although recent advances, research on multimodal GUI-agents and web automation still GUI automation has important gaps. Recognising these gaps helps motivate work on building a lightweight, DOM-summarising, fallback-enabled agent architecture. Blow are the listed critical gaps:

\begin{enumerate}
    \item \textbf{Unreliable element grounding:} While multimodal like SeeAct \cite{SeeAct} generate action from screenshot images, they rely on mapping of the generated outcome and DOM. SeeAct \cite{SeeAct} provides three grounding strategies, still all of them struggle with grounding and drop agent performance due to element grounding limitation.SeeAct \cite{SeeAct} motivates us to work on element grounding, where instead of relying only on the key pair comparison, we directly ask the LLM for the exact grounding value.

    \item \textbf{Privacy concern and Human-in-Loop:} GUI agents become more autonomous and powerful, which raises concerns about security, privacy, and safe execution. Survey \cite{tang2025surveymllmbasedguiagents} \cite{ning2025surveywebagentsnextgenerationai} call out deficiencies in safety-aware execution control and benchmark standardisation.

    \item \textbf{Large and complex DOMs, missing js, css:} Real-world websites contain thousands of DOM elements, where model has their input limitation beyond which they won't work \cite{wang2025guiagentsfoundationmodels}. Model does not look at JS or CSS while inference, thus loses the context where the user prompt contains context about visual values \cite{wang2025guiagentsfoundationmodels}. 
    
    \item \textbf{Cost and Token Inefficiency with Large Models:} Using large multimodal models (like GPT-4V) along with full HTML/DOM inputs and images is resource-intensive and often infeasible for small-scale or low-resource environments, which raises concern regarding cost and input limitations \cite{tang2025surveymllmbasedguiagents}.

    \item \textbf{Stateless DOM processing:} All recent DOM reduction approaches \cite{zhang2025prune4web} \cite{lai2024autowebglm} \cite{schiepanski2025d2snap}  process each snapshot independently, which misses an obvious efficiency signal: in most multi-step tasks the page only changes in a small region between one step and the next. Agent-E's change observer \cite{tarsariya2024agente} is the only system that looks at DOM change across steps, but it uses real-time browser events to \textit{describe} what happened (action feedback) rather than to \textit{reduce} what is sent to the grounder, so it increases tokens instead of saving them.

    \item \textbf{Under-studied sub-6B local grounders:} The accuracy story in the literature is almost entirely told through GPT-4 class models \cite{SeeAct} \cite{zhang2025prune4web}, while the deployment story needs a local grounder. With QLoRA \cite{dettmers2023qlora} and modern small open-weight models like Qwen2.5 \cite{qwen25techreport2024}, it is practical to check how close a sub-1B grounder can get on Mind2Web-style element accuracy, but very few papers report this number head-to-head against the GPT-4o baseline.

    \item \textbf{Privacy and safety bolted on post-hoc:} Surveys \cite{tang2025surveymllmbasedguiagents} \cite{ning2025surveywebagentsnextgenerationai} repeatedly call out safety-aware execution and privacy as open concerns, but the pipelines that address DOM reduction and grounding do not design for privacy at the filter/grounder interface. Personally Identifiable Information (PII) in form fields, password placeholders, and identification numbers end up in the LLM context by default, and human-in-the-loop gates are usually added as a final confirm step rather than as a risk-aware layer that runs before grounding.
\end{enumerate}
